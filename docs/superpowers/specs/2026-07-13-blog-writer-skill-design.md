# blog-writer Skill 设计

- 日期：2026-07-13
- 状态：待实现
- Skill 名：`blog-writer`
- 安装位置：`.claude/skills/blog-writer/`

## 1 背景与目标

用户有一个 Obsidian + Quartz 的嵌入式技术博客（Quartz 4.5.2，文章在 `content/` 下按主题分类）。痛点是「想把经验记下来，但不想花大量时间记录和整理」。

本 skill 的职责：把用户随手写的**凌乱草稿**，整理成符合博客规范、风格统一的专业文章。

风格目标：详细但不啰嗦，说人话讲重点，新手可无脑复现，老手不失专业性，**AI 味淡**。

## 2 三条红线（写进 SKILL.md 顶部，每次必守）

1. **尊重草稿，不编事实**：草稿里没有的具体数据、调试结论、代码行为、硬件现象，绝不编造。只补「常识」——标准函数原型、语言定义、通用术语。
2. **补的必标**：预览时高亮所有 skill 补充的内容，让用户一眼定位。
3. **去 AI 味**：对齐用户现有文章的平实笔触，禁用 AI 腔。

AI 味黑名单：
- 禁：套话开场/收尾（「在嵌入式开发中…」「希望本文对你有帮助」「综上所述」「值得注意的是」）
- 禁：煽情升华（「让我们一起来探索」「开启旅程」「赋能/抓手/闭环」）
- 禁：工整排比、对仗堆砌、每段强行三段式
- 禁：空洞强调（「非常重要」「至关重要」「不可或缺」）
- 禁：滥用 emoji、标题党
- 学：短句收束（「就这一个参数的区别。」）——直接、有信息密度

## 3 文件结构

```
.claude/skills/blog-writer/
├── SKILL.md                    # 主流程 + 三条红线，精简
└── references/
    ├── writing-style.md        # 从用户真实文章提炼的风格指南
    ├── article-structures.md   # 5 类文章骨架
    └── frontmatter-spec.md     # 统一 frontmatter 规范
```

遵循 progressive disclosure：SKILL.md 精简以保证触发可靠，详细规则放 references/，按需加载、各自独立、好维护。

## 4 工作流（7 步）

1. **拿草稿**：用户给草稿文件路径（在 Obsidian 里写好后 `@文件`），或直接把草稿贴进对话。skill 两种都支持。
2. **判类型**：扫内容，从 5 类骨架中选一类。
3. **补常识**：补函数原型、标准定义、术语；同时把草稿里**没写清的关键数据/结论/代码行为**记下来。
4. **一次性反问**：把上一步记下的疑点**一次问完**（不挤牙膏），用户简短答即可。
5. **成稿**：按骨架 + 风格整理成完整文章，配好 frontmatter，定好分类和文件名。
6. **预览**：在对话里给完整成稿（含 frontmatter、目标路径、文件名）；skill 补的内容用 `【补充】` 前缀标注，方便用户定位（终端里 `==` 高亮不渲染，所以用前缀）。
7. **落盘**：用户点头 → 写入 `content/<分类>/<文件名>.md`；要改就说。

## 5 风格指南（references/writing-style.md）

- **标题**：正文统一从 `## 1` 开始（first-level 2，因为 Quartz 把 title 渲染成 h1，正文用 `#` 会撞），子节 `### 1.1`，最多 3 级。
- **代码**：标语言；关键行加中文注释；错写法和对写法**放一起对比**。
- **表格**：对比、参数、引脚、考点——能用表格就别写大段文字。
- **引用块 `>`**：放报错原文、重要提示、datasheet 摘录。
- **笔触**：平实口语 + 短句收束；技术词用代码格式（`sizeof`），正文中文。
- **收尾**：给「要点速查」表格，浓缩考点。

## 6 文章骨架（references/article-structures.md，5 类）

| 类型 | 用户范例 | 骨架 |
|---|---|---|
| 踩坑记录 | sizeof vs strlen | 起因 → 问题代码(错 vs 对) → 根因分析 → 要点速查 → 参考代码 |
| 外设/知识讲解 | PN532 模块介绍 | 概述/特点 → 关键参数(模式/引脚) → 接线/配置表 → 用法 |
| 项目连载 | PN532 移植系列 | 背景目标 → 本篇子题 → 问题与解决 → 成果/代码 |
| 随笔/方法论 | 红蓝标记法 | 痛点 → 思路 → 步骤/实例 → 要点 |
| 工具/环境教程 | STM32 开发环境搭建 | 为什么用 → 装什么 → 怎么配 → 验证 |

骨架是「参考」不是「模板」——内容不够的段直接省，不强凑。

## 7 frontmatter 规范（references/frontmatter-spec.md）

```yaml
---
title: 标题                              # 必需
date: 2026-07-13                         # 发布日，YYYY-MM-DD
description: 一句话讲清这篇讲什么          # 强烈建议，列表/RSS/SEO 用
tags:                                    # 必需，2-4 个；Quartz 靠它生成分组页
  - STM32
  - DMA
draft: false                             # 可选，true=草稿不发布
number headings: first-level 2, start-at 1, max 3, 1.1, auto, contents toc
---
```

关键变更（借这次机会统一用户现有文章的不一致）：
- 砍掉 `categories`——Quartz 只认 `tags` 生成分组页，`categories` 没实际作用。
- 不再手写 `created`/`updated`——让 Quartz 从文件系统/git 自动取 modified，只留 `date` 作发布日。
- `number headings` 统一 `first-level 2`（正文从 `##` 开始）。

落盘默认 `draft: false`（已过预览确认）；用户想先存草稿再润色，可让 skill 设 `draft: true`。

## 8 分类与命名

- **分类目录**：`MCU/STM32`、`MCU/FreeRTOS`、`Linux`、`项目`、`硬件基础/硬件与协议`、`工具与方法`、`随笔`、`编程语言/C语言`。
- **文件名**：简洁中文描述名，保持现有风格（如 `DMA缓存一致性问题.md`、`sizeof vs strlen：从一次 fwrite 踩坑说起.md`）。
- **项目连载**：放对应项目子目录（如 `content/项目/PN532驱动库移植_基于SMT32L4/`）。
- skill 按内容判断分类 + 文件名，预览时告知用户，用户可改。

## 9 边界处理（草稿不完美时）

- **太短/信息严重不足** → 不硬凑，列出缺的关键信息问用户。
- **自相矛盾**（代码和结论对不上）→ 指出来，不擅自选边。
- **分类模糊** → 预览时给倾向 + 让用户定。
- **没把握的硬件/寄存器/时序细节** → 留 `【待确认】` 占位，绝不编。

## 10 成功标准

- 给一段凌乱草稿，skill 能产出符合上述规范和风格的完整文章。
- 预览环节齐全：完整成稿 + frontmatter + 目标路径 + 高亮补充内容。
- 产出文章 AI 味淡，笔触接近用户现有文章（如 sizeof vs strlen 那篇）。
- 不编造草稿里没有的技术事实。
- 文章落盘到正确的 `content/` 子目录，文件名为中文描述风格。
